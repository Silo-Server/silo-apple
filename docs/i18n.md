# Translating the Apple apps

The apps' text comes from one shared catalog, `Silo-Server/silo-translations`, that also
feeds the web, Android and Roku clients. This page covers how strings reach the Apple apps
and how code should use them.

## Where strings live

- `iosApp/iosApp/Localizable.xcstrings` is generated. Never edit it, in Xcode or by hand.
  Every entry is `extractionState: manual`, and Xcode turns each key into a
  `LocalizedStringResource` symbol: `common.cancel` becomes `.commonCancel`, and
  `home.section.recentlyAddedIn` becomes `.homeSectionRecentlyAddedIn(_:)`. An underscore
  starts a new word too: `catalog.extra.behind_the_scenes` becomes
  `.catalogExtraBehindTheScenes`, and so does a letter after a digit:
  `watchParty.seat.a11yHost` becomes `.watchPartySeatA11YHost`.
- Arguments are positional and unlabeled, in the key's placeholder order, except the
  labelled count described under **Counts** below.
- `.silo-translations` records which catalog version produced it, and `.silo-translations-files`
  lists the generated files, so a later sync removes a language that stopped shipping.
- The three apps build the catalog from `iosApp/`. Top Shelf, the notification service and
  the downloads Live Activity list it in `project.yml`, so each gets its own copy.
- `iosApp/InfoPlist/<platform>/InfoPlist.xcstrings` holds each app's permission prompt
  text, generated from the catalog's `apple.infoPlist.*` keys. Keep their English
  identical to the app's `Info.plist`.
- A language ships when the catalog translates something into it. The language picker and
  device-language matching read the bundle's localizations, so there is no list to update.

## Adding or changing a string

1. In a silo-translations checkout, branch from its main branch and add the key to
   `catalog/en.arb` with a `description`. Say where the text appears and what each
   placeholder holds, in argument order ("1: series name, 2: episode number"). Apple
   arguments are positional and unlabeled, so that description becomes the only hint at
   the call site. Run `make fmt` and `make check`.
2. In this repository, run:

   ```sh
   scripts/sync-translations --local <silo-translations checkout>
   ```

   Commit the catalog, `.silo-translations` and `.silo-translations-files` with the code that
   uses the key.
3. Once silo-translations publishes releases, `scripts/sync-translations --version <v>`
   pins one. CI then checks that the committed catalog matches it. Until then, check a
   local pin by running the command from step 2 against the same commit, then
   `git diff --exit-code -- iosApp/iosApp/Localizable.xcstrings iosApp/InfoPlist .silo-translations .silo-translations-files`.

While text is being moved into the catalog, its English stays exactly as it was. Wording
fixes go in their own small PRs.

## Call sites

The root view sets `\.locale` and `\.layoutDirection` to the profile's app language, so
SwiftUI text switches as soon as the language changes, with no relaunch.

Some keys in these examples are illustrative.

**In a view**, pass the symbol:

```swift
Text(.commonCancel)
Button(.commonCancel, role: .cancel) { dismiss() }
Text(.detailSeasonCount(seasons))           // plural on its count
.navigationTitle(Text(.settingsAppLanguageTitle))
```

**From a model or view model**, return `LocalizedStringResource` and let the view render
it. Don't return a `String`:

```swift
enum DownloadState {
    case paused, complete
    var label: LocalizedStringResource {
        switch self {
        case .paused: .downloadsStatePaused
        case .complete: .downloadsStateComplete
        }
    }
}

Text(state.label)
```

**When a `String` is needed outside a view** (an accessibility label built in code, Top
Shelf, an `errorDescription`), resolve it through `AppLanguage.string(_:)`:

```swift
collection.title = AppLanguage.string(.homeSectionContinueWatching)
```

`String(localized:)`, `NSLocalizedString` and `Bundle.localizedString(forKey:)` use the
process language, not the app language. `scripts/ci/check-string-localized.sh` blocks
them outside `AppLanguage.swift`.

**Text that isn't interface text** (a name, a number, a server value, or English a
model outside the catalog still writes) stays as it is: `Text(verbatim:)` in a view,
or `.verbatim(text)` where an API takes a `LocalizedStringResource`. Text that is
stored, sent to the server, matched or compared is data and stays English in every
language; translate only what is shown, and split a shown label from the stored value
when one code path builds both.

When that English comes from the same label helpers the screen uses (track and
quality labels in the Remote Control state the Apple TV sends to the phone), build it
inside `AppLanguage.inEnglish { … }`: `AppLanguage.string(_:)` resolves in English
while the closure runs.

**Extensions without `AppLanguage`.** The downloads Live Activity renders in its own
process and doesn't compile `AppLanguage`. The app puts the language on screen in the
activity's content state (`language`, plus `formatLocale` for numbers), and the widget
sets `\.locale` from it, so its `Text(.symbol)` and numbers match the app.

**Counts.** Apple formats an integer placeholder with the locale's grouping ("1,234").
A count that can pass 999 therefore goes into the message as a `{count_text}` string next
to the plural's `{count}`, and a number that is an identifier (a season numbered 2021, a
chapter) is a `String` placeholder, so English keeps its digits. Pass those strings through
`LocaleFormat.integer(n)`: no grouping, and the language's own digits (Arabic-Indic in
Arabic). Never `String(n)` or `"\(n)"`. Xcode rejects a plural whose forms don't print the
number, so when any English form leaves it out (a `{count_text}` message, or labels such as
"Author"/"Authors") the generator writes the substitution form, and the symbol labels the
count: `.downloadsSelectCount(count: n, LocaleFormat.integer(n))`.
A library's size, a collection card's count, and a person page's title count use
`LocaleFormat.groupedCount(n)` instead, which adds the locale's thousands separator
("1,284 movies", "1.284 Filme").

**When a view needs a `String`** (a component that takes `String`, such as
`EmptyStateView`, a label joined with server text, a length estimate), read `\.locale`
and pass it to `AppLanguage.string(_:locale:)`, so the view re-renders when the language
changes. `Text(.key)` re-renders on its own.

```swift
@Environment(\.locale) private var locale

EmptyStateView(icon: "heart", title: AppLanguage.string(.personalFavoritesEmpty, locale: locale))
```

**Plurals** are one ICU message per count (`{count, plural, one {# season} other {# seasons}}`),
never an `s` added in code. A shown label never doubles as a stored or compared value:
keep the raw value (a `rawValue` saved to `UserDefaults`, a filter value sent to the
server) and add a separate `LocalizedStringResource` label.

**App Intents metadata** needs compile-time values, so it takes the key as a literal:
`static let title: LocalizedStringResource = "shell.searchIntent.title"`. App Shortcut
phrases are read from an `AppShortcuts.xcstrings` file, which the catalog doesn't generate
yet, so they stay English.

**Text the server wrote** (section titles, problem details, settings-manifest labels)
goes through `AppLanguage.serverText`. It shows the catalog's translation when the
language on screen translates the key. Otherwise it shows the server's text, and in
English it always shows the server's text as sent. A view passes the language from
`\.locale`, so the text switches with the app:

```swift
@Environment(\.locale) private var locale

HomeSectionHeader(title: section.displayTitle(in: locale))
```

- Problem details use `problem.localized(text)`. In order, it tries
  `error.field.<code>` for the first field error, then `error.<type>`, then the server's
  `detail`.
- Manifest labels use `SettingPresentationMetadata.unsetLabel(for:fallback:)`.

**Names and titles joined into text outside the catalog** go through
`AppLanguage.isolated(_:)`. In a right-to-left language it wraps them in Unicode isolates,
so punctuation stays in place. Left-to-right output is unchanged. Catalog placeholders that
SwiftUI formats are isolated by the system.

## Numbers, dates and names

Format with the app's language, never `Locale.current`: the process locale doesn't follow
the in-app language until the next launch.

- In a view, `Text(date, format: …)` and `Text(n, format: …)` take the root's `\.locale`.
- Anywhere else, use `Shared/LocaleFormat.swift`: `integer`, `decimal`, `percent`,
  `rate`, `clock`, `duration`, `bytes`, `ordinal`, `languageName`, `dateFormatter`. Each
  takes a `locale:`; a view passes its `\.locale`, and other code gets
  `AppLanguage.formattingLocale`, which is English inside `AppLanguage.inEnglish { }`.
- A `.formatted(…)` or `Date.FormatStyle` outside a view adds `.locale(…)`.
- US English output is byte for byte what the app printed before: decimals still round
  as `printf` does, and English sizes keep `ByteCountFormatter` ("2 KB", not "2 kB").
- `AppLanguage.locale(for:)` keeps the device's region, calendar and hour cycle, as the
  system does once the app's `AppleLanguages` holds the language. Arabic writes
  Arabic-Indic digits unless the user chose other digits.
- Values that are sent, stored, matched or used as ids (a speed option id, a
  `Content-Length`, a file id) stay POSIX.
- Language names are shown in the app's language. A track title that repeats the
  language's English name ("English 5.1") still counts as repeating it.

## Right to left

The root sets `\.layoutDirection`, and SwiftUI mirrors stacks, alignment, padding and
`.offset(x:)`.

- Use the semantic symbols for direction: `chevron.forward`/`chevron.backward`,
  `arrow.forward`/`arrow.backward`, `arrow.up.forward`. They draw the same in English and
  flip in a right-to-left language; `chevron.right` doesn't.
- Media transport and timelines read left to right in every language: put
  `.mediaLayoutDirection()` on the transport row, the scrubber and its time row, not on
  the whole player. Poster overlays keep their physical corners.
- Siri Remote and pan gestures report physical directions. A handler that maps left or
  right to previous/next or to a panel on one side reads the direction through
  `MoveCommandDirection.inLayout(layoutDirection)` (tvOS), or flips its sign from
  `\.layoutDirection`.

## Converted code stays converted

`scripts/ci/catalog-text-paths.txt` lists the directories and files whose text all comes
from the catalog. In those, `scripts/ci/check-catalog-text.py` fails on:

- English in the first argument of a SwiftUI text API, including either branch of a
  ternary, a `??` fallback and an interpolation: `Text("Done")`, `Button(busy ? "Saving…" : "Save")`,
  `.navigationTitle("Profiles")`, `.accessibilityLabel(name ?? "Unknown")`;
- prose passed to a labelled text argument of any call (`title: "No favorites"`,
  `message: isOn ? "On" : "Off"`). Identifiers (`"chevron.backward"`) and logging calls pass;
- in a path listed with the `mappings` flag, prose mapped to shown text outside a call:
  `return "…"`, `case .x: "…"`, a ternary branch, a `??` fallback or `.append("…")`.

It reads calls and literals that span lines, and multiline `"""` strings. Add a path to the
list once every string it shows is converted. A line that must keep a literal (a brand
name, a technical token such as "HDR", a value that is sent or stored) ends with
`// i18n-ignore: <reason>`.

To check a converted screen by eye, run a Debug build with the launch arguments
`-AppleLanguages "(en)" -NSAccentuateLocalizedStrings YES`: catalog text shows
accented, and anything plain is server data, `.verbatim` text, or a string that was
missed. Plural strings break under this flag (they show as `@v…`), and so do integer
specifiers; that is the flag mangling the format, not a catalog fault.

## Tests

Tests render English from the real catalog. Don't assert translated strings. To test
lookup rules, replace `AppLanguage.catalogLookup` with a small table, as
`Tests/ServerTextTests.swift` does.
