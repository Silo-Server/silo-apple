Requests on iPhone & Apple TV

Bringing the server's media-request system to iOS and tvOS. The web app already ships a full Discover / Yours hub; Android shipped phone + TV clients. These mockups adapt the same one-tap contract to each Apple surface, following how people actually use requests.

Job 1 · Capture the impulse

“Someone just mentioned a movie.” This happens on the phone, and the user's first instinct is to search the library. The request affordance must live inside search — the moment the library comes up empty is the moment the request happens, with the query already typed.

Job 2 · Fill the gap on the couch

“Nothing to watch → I looked for it → it's not here.” On the TV the same rule applies, but typing is expensive — so the existing Search screen does double duty. A separate hub that makes you re-type the title would be the failure mode.

Job 3 · Track the pipeline

“Where's my movie?” — checked like a package tracker, mostly on the phone, occasionally on TV. Needs a findable home (hub + My Requests), glanceable status language, and a straight jump into the library the moment a request lands.

01iPhone — request from search

The primary entry point. Library results render first, exactly as today. When the library can't fully answer the query, an “Available to request” section appears below with TMDB matches — the same inline weave the web app uses in ⌘K search. Every card carries server-computed state, so a user can never double-request: requestable cards get the white pill, everything else shows why not.

The deliberate destination for browsing and tracking. Trimmed from the web version: no studio/network/genre brand-browse in v1.

iOS · Entry point Profile menu, not a fifth tab — the same call Android made. The tab bar stays a pure consumption surface (Home / Libraries / For You / Calendar, + Downloads when enabled); Requests joins the personal-shelf cluster in the avatar menu. The whole feature is hidden unless the server reports requests_enabled. Alternative if discoverability worries you: a conditional tab à la Downloads — flagged as an open question below.

03iPhone — request detail & My Requests

A request detail page that reads like a real title page, not a form — backdrop, poster, meta, synopsis — with exactly one primary action computed from server state. No confirmation dialog: the button itself is the confirmation, and it morphs into the status pill on success (matching web + Android).

iOS · My Requests The package tracker. Same three buckets as the web's “Yours” tab (In motion / Landed / Needs attention). Swipe-to-cancel on pending requests (the server allows owner-cancel until submission). Quota shown quietly in the corner — users learn the limit before hitting the 429, not after. Completed rows deep-link into the real library item.

04Apple TV — request from Search

The single most important tvOS decision: don't build a second keyboard. The existing Search screen grows one row. Library results stay primary; below them, an “Available to request” row appears for what the library can't answer. The query the user already suffered through the grid keyboard for is reused for free.

07One status language, both feet

The server's lifecycle (status × outcome) collapses into five user-facing states. Skyline is monochrome by charter — so chips stay monochrome and the only color is a 6-pt dot (precedent: the amber rating badge is Skyline's one sanctioned chromatic token). iOS uses the identical mapping so the two platforms read as one system.

User-facing stateServer stateDotBehavior
Pending status=pending · outcome=activeAmber (pulsing) Cancelable by the requester. “Waiting for approval.”
On the way approved / queued / downloadingSky Per-target detail (1080p ✓ · 4K 62%) on My Requests rows; single chip elsewhere.
In your library completed + library_content_idEmerald The chip becomes a door: press/tap opens the real item. Request UI retires itself.
Needs attention outcome=declined / failedRose Shows the admin's decline reason verbatim; failed requests can simply be re-requested (server auto-clears them).
Unavailable requestable=false (limit / disabled / blocked)Neutral Quiet reason label; the Request affordance simply never renders. Nothing to press, nothing to fail.
