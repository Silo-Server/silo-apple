## Gap detail

### 1. wedge-recovery-chain

**Verdict:** `missing`  ·  **Severity:** `high`

**What AE fixed / what we have.** AE's cluster is a staged wedge-recovery chain: a play-intent-gated wedge detector that re-anchors the producer, a deadline-bounded seek with a buffer-based starvation predicate, bounded re-anchor/reload gates, a fetch-counter stall watchdog with nudge→item-reload stages, pre-first-frame -15628 escalation, a spurious-pause reassert, a bounded revive for items killed by failedToPlayToEndTime, and a bounded VOD muxer-death producer rebuild. We independently built most of this: an intent-based isUserPaused (pause false-positives covered), a 1 Hz playhead watchdog with serve-quiet gating that runs performVODStallRecovery (nudge, then in-place item reload, riding an authoritative producer restart at the pending-seek anchor), a 3-per-90s reanchor cap escalating to a Compatibility-route fallback AE lacks, a startup fetch-freeze ladder with -15628 errorLog escalation and a 60s backstop, producer-side park escapes (.vodStartupConsumerWedge/.vodMoovBlocked, landed today in 359d20c), and muxer death surfacing through reportError into the route ladder instead of a silent black screen. Three members are genuinely unenforced, and they gate each other: (1) no deadline-bounded seek — isSeekPending is cleared only by the seek completion, and both the playhead watchdog and edge watchdog hard-guard on !isSeekPending, so a wedged unlanded seek (AE's original #65 scrub-burst trigger) disarms ALL steady-state recovery; the M7 anchor vodPendingSeekMediaTarget is only alive precisely while the watchdog is disarmed, and the completion's seekItem === currentItem guard can latch isSeekPending true forever if an item reload races a pending seek; (2) no item-death revive — the failedToPlayToEndTime handler only acts on "Playlist File unchanged"/-12888 and returns for everything else, while a dead item parks at .paused, which fails believesPlayable in every watchdog arm (the starvation arm requires .waitingToPlayAtSpecifiedRate) — terminal frozen session with no error and no route fallback, and our vodSegmentMissResolver holds miss responses up to 8s, comfortably past AVPlayer's ~3.5s TTFB window, making -12889 accumulation during producer restarts realistic; (3) no spurious-pause reassert. Additionally the watchdog has a dead zone (generatedAhead < 12 while bufferedAhead >= 2 satisfies neither arm), adjacent to the deliberately-deferred steady-state backpressure detector (known open, flagged as overlap).

**The gap.** Three enforcement holes in AVPlayerBackend's otherwise-solid recovery chain: (1) unlanded seeks have no deadline and disarm the playhead+edge watchdogs via the !isSeekPending guards (plus an isSeekPending latch leak when the completion's seekItem === currentItem guard eats the clear after an in-place item reload); (2) failedToPlayToEndTime deaths other than -12888/playlist-unchanged are ignored, and the dead item's .paused state gates off every watchdog arm — no bounded revive, no route-fallback escalation; (3) no bounded play() reassert for a spurious .paused during recovery. Plus a watchdog dead zone (bufferedAhead >= 2 && generatedAhead < 12 trips neither arm) overlapping the known-open deferred backpressure detector.

**Our exposure.** (a) User on a high-RTT remote connection scrubs while the producer is restarting: segment fetches wait out the 8s miss window, AVPlayer accumulates -12889 media timeouts and posts failedToPlayToEndTime; the item parks rate-0/.paused with isUserPaused=false; recoverLocalLoopbackFailureIfNeeded returns (error is not -12888), believesPlayable is false in every playhead-watchdog arm, and the starvation escalation requires .waitingToPlayAtSpecifiedRate — the session freezes forever with no spinner-timeout, no error, and no PlayerCore fallback until the user force-exits. (b) A zero-tolerance in-item seek whose completion never fires (loader poisoned post-startup by -15628, which our errorLog handler only escalates pre-first-frame) leaves isSeekPending latched true, permanently disarming loopbackPlayheadWatchdogTick and sampleLocalLoopbackEdge — frozen picture at the pre-seek frame, indefinitely.

**Recommendation.** In iosApp/iosApp/Screens/Player/AVPlayerRoute/AVPlayerBackend.swift: (1) deadline-bound seek(to:): arm an ~8-10s timer racing the completion; on expiry, classify with AE's seekIsWedged predicate (forward loadedTimeRanges at the target vs. renderedTime — bufferedEnd-renderedTime < ~1s = starved, climbing = healthy-slow), clear isSeekPending while preserving vodPendingSeekMediaTarget as the recovery anchor so loopbackPlayheadWatchdogTick can run performVODStallRecovery at the TARGET; also clear isSeekPending in the completion even when seekItem !== currentItem (latch leak). (2) In recoverLocalLoopbackFailureIfNeeded, treat any failedToPlayToEndTime with !isUserPaused as item death: add an ItemDeathReviveGate-style bound (attempts reset on >0.5s position change, cap ~3) driving the existing in-place item-reload path (performVODStallRecovery attempt>=2 / reloadLoopbackStartupItem pattern) with the .paused gating explicitly bypassed, escalating to onLoopbackStallUnrecoverable ("item_death") -> attemptSiloRouteCompatibilityFallback when exhausted. (3) In loopbackPlayheadWatchdogTick, add a bounded reassert: timeControlStatus == .paused && !isUserPaused && reasonForWaitingToPlay == nil for N consecutive ticks -> avPlayer.play(), max ~3 per reanchor window. (4) When closing the dead zone, either drop playheadWatchdogMinGeneratedAhead below the reanchor threshold or add an arm for bufferedAhead >= 2 && generatedAhead < 12 — coordinate with the deliberately-deferred steady-state backpressure detector (known open) rather than duplicating it.

### 2. host-item-reuse-pip-airplay-nowplaying

**Verdict:** `missing`  ·  **Severity:** `medium` — ⚠️ UNVERIFIED (refuter hit session limit)

**What AE fixed / what we have.** AE hardened its NativeAVPlayerHost so the AVPlayer instance survives internal reloads (keepNativeHost + terminal-flag clear + pause-before-swap), PiP survives recovery reloads (inPlaceSwap), AirPlay works from the loopback server (0.0.0.0 bind + LAN-IP URL swap on isExternalPlaybackActive), Now Playing metadata replays onto every fresh item, backgrounding tears the video pipeline down (mediaserverd wedge), and re-selecting the live audio track is a no-op. Most of this cluster is covered in silo-apple by different mechanisms: AVPlayerBackend already reuses one AVPlayer across audio-switch/reanchor/recovery reloads via replaceCurrentItem, teardownMediaPipeline pauses before the item swap and clears per-session state, Now Playing is decoupled from AVPlayer items entirely (MPNowPlayingInfoCenter + MPRemoteCommandCenter owned by PlayerViewModel, so item swaps and even full player recreation on episode autoplay cannot blank Control Center, and the tvOS-26 externalMetadata artwork crash cannot occur), tvOS backgrounding fully disposes the player via suspendForBackground() (stronger than AE's fix), VOD stall recovery already does an in-place item reload with no pre-pause/nil-item gap, and disc/video-to-music members are architecturally N/A. Two genuine gaps remain: (1) AirPlay on the primary loopback route is broken — the loopback server binds 127.0.0.1 only, allowsExternalPlayback is never configured (AVPlayer default true), and there is no isExternalPlaybackActive observer or LAN-host URL swap, so an AirPlay receiver is handed an unreachable 127.0.0.1 URL; (2) re-selecting the already-active audio track has no no-op guard at any layer and triggers a full loopback pipeline rebuild (new writer + server + item), the exact pointless stall-prone reload AE #3.4 eliminated. PiP-survival members are not applicable on main (the AVPlayer route has no PiP; PiP exists only on PlayerCore's sample-buffer layer) but become live when the unmerged feature/ios-pip branch lands, since the audio-switch reload path's pause+nil-item teardown would invalidate AVKit's PiP content source.

**The gap.** No AirPlay support on the loopback route: LoopbackSegmentServer binds 127.0.0.1 only, avPlayer.allowsExternalPlayback is left at its default (true) with no isExternalPlaybackActive observation, no LAN-IPv4 host swap, and no explicit opt-out — external playback engages and hands the receiver an unreachable localhost URL (AE #86). Secondary hole: no re-select no-op guard for audio tracks — PlayerViewModel.selectAudio and AVPlayerBackend.selectAudioTrack rebuild the entire loopback pipeline when the user re-picks the already-active track (AE #3.4).

**Our exposure.** (1) User playing any movie on the primary SiloPlayer loopback route on iPhone/iPad picks an AirPlay target from Control Center or the system route picker: AVPlayer switches to external playback and sends http://127.0.0.1:PORT/master.m3u8 to the Apple TV/receiver, which cannot connect — the TV shows a black screen/endless spinner while the phone says it is playing there; there is no recovery path back short of deselecting the route. An SDR-only receiver would additionally reject the DV/HDR master even if it could reach the server. (2) User opens the iOS audio menu (MobilePlayerControls trackSelectionMenuContent) or tvOS HUD (TVPlayerInfoHUD) and taps the track that is already checked: full teardownMediaPipeline + new writer/server/item — several seconds of black/buffering respin for a no-op request, plus a burned seek-cache/producer warmup. (3) Forward-looking: once feature/ios-pip merges, an in-PiP audio-track switch on the AVPlayer route goes through load(strategy:)'s pause + replaceCurrentItem(nil) teardown, which invalidates AVKit's PiP content source and dismisses the PiP window (AE #93 failure mode).

**Recommendation.** Short-term AirPlay fix: in AVPlayerBackend.prepareAssetPlayback (iosApp/iosApp/Screens/Player/AVPlayerRoute/AVPlayerBackend.swift), explicitly set avPlayer.allowsExternalPlayback = false when currentSourceStrategy is .siloLoopback so AirPlay degrades to screen mirroring (works today, just lower quality) instead of a dead external session; keep it true for .remoteHLS/.remoteDirect where the URL is receiver-reachable. Full AE-parity fix: bind LoopbackSegmentServer (LoopbackSegmentServer.swift) to all interfaces (0.0.0.0) guarded by the existing random port + an unguessable session-path token, observe avPlayer.isExternalPlaybackActive in attachItemObservers, and on activation reload the current item with the URL host swapped to the device LAN IPv4 (synchronous getifaddrs en* scan, prefer en0, as AE's HLSLocalServer.lanIPv4 does), reloading back to 127.0.0.1 on deactivation; route SDR receivers to the media playlist via LocalHLSPlaylistPolicy to dodge the DV/HDR master rejection. For the re-select hole: add an early return in PlayerViewModel.selectAudio (iosApp/iosApp/Screens/Player/PlayerViewModel.swift:4290) when selectedAudioId == track.trackId, and a belt-and-suspenders guard in AVPlayerBackend.selectAudioTrack comparing against the spec's currently-selected loopback track. When feature/ios-pip lands, convert the audio-switch loopback reload to the in-place pattern performVODStallRecovery already uses (no pre-pause, old item alive until replaceCurrentItem) or gate the teardown on PiP being inactive.

### 3. segment-planning-cutting

**Verdict:** `partial`  ·  **Severity:** `medium`

**What AE fixed / what we have.** AE's cluster fixed (a) DTS-keyed cut routing that split open-GOP IRAPs from their RASL leaders (#92), (b) trusting sparse/clustered keyframe indices that planned one enormous segment (#64/#91, two witnesses: max gap and coverage), (c) uniform plans anchored at PTS 0 that advertised frameless leading segments on late-start titles (#64), and (d) unbounded libavformat-interleaver RAM on any long segment under +frag_custom, fixed by a session-long ~2x-target buffered-DTS flush bound with early ftyp+moov emission (#64). Our loopback route ports (a)-(c) essentially verbatim: LoopbackSegmentCutter is AE's VODSegmentCutter (decode-order, keyframe-PTS-gated, end-fence clamp), LoopbackSegmentPlan.keyframeIndexIsTrustworthy enforces both the gap and coverage witnesses with a uniform-stride fallback, and buildUniformPlan anchors at the first indexed keyframe. We additionally enforce a stronger runtime form of the #92 probe check via resume-anchor bitstream validation (probeSegmentOpener NAL-walk + segment coalescing), and today's 359d20c covers the delay_moov/init.mp4 half of #64 (moov priming flush, first-flush double-flush, .vodMoovBlocked escalation). The one hole is (d): our interim fragment flush (every 1.5s of routed video) runs only while vodProgressiveAccumulating is true, i.e. only while the FIRST segment of a producer session is open (segmentEntries.isEmpty); segments after the first have no buffered-span bound and rely solely on plan-time gating to keep segments short, and even the anchor-path flush drains into in-memory buffers (pendingSegmentBytes + store progressive Data have no disk spill), unlike AE which drains to a staging file.

**The gap.** No session-long mid-segment flush bound: after the first segment of a producer run is finalized, libavformat's interleaver buffers each segment's entire span until the plan cut (movflags +frag_custom), with no AE-style ~2x-target buffered-DTS cap. The plan-trust gate bounds keyframe-plan segments only to ~34s (30s trusted gap + 4s target), and uniform-plan cut points depend on the source's real keyframe cadence, which is exactly what an untrusted index failed to describe. Additionally, the anchor-segment interim flush releases interleaver memory into pendingSegmentBytes and the store's progressiveSegments dictionary, both plain in-memory Data with no spill, so a segment that never cuts migrates the RAM growth rather than capping it.

**Our exposure.** Two scenarios. (1) Rare but hard failure: an MPEG-TS/M2TS source whose index is untrusted (uniform plan) and whose real bitstream has very sparse or absent keyframes after the head — the cutter can only advance on real keyframes, so a segment spans the full real GOP; mid-session this buffers that whole span in the interleaver, and if it is the never-finalized first segment the whole title accumulates in pendingSegmentBytes + store progressive Data instead (AE measured ~13GB on a 110-min title). On Apple TV (~2GB app memory ceiling) this is a jetsam kill mid-playback with no route-ladder fallback, since the process dies rather than the session erroring. (2) Common-shape degraded case: a high-bitrate remux whose keyframe gaps legitimately approach the 30s trust cap buffers up to ~34s of 4K video (~300-450MB at 80-100Mbps) per segment in the interleaver between cuts, causing large transient memory spikes and eviction pressure against the seek cache on tvOS.

**Recommendation.** Extend the interim-flush machinery in LoopbackSegmentWriter to run session-long, AE-style: in vodCutBeforeVideoPacketIfNeeded, track routed-video PTS span since the last flush without the vodProgressiveAccumulating gate (keep the 1.5s cadence for the progressive anchor window; use a ~2x targetSegmentDuration bound, i.e. 8s, for post-anchor segments) and set vodInterimFlushRequested accordingly; in performVODInterimFragmentFlush, drop the vodProgressiveAccumulating guard but keep the moov-wedge guard (vodAudioNeedsParsedPacketForMoov && !initSegmentWritten && !vodAudioPacketRouted) so the mid-segment flush appends additional moof+mdat pairs into the open pendingSegmentBytes via the existing box sink (fMP4 segments tolerate multiple fragments, same as the anchor path already proves). Guard the sentinel/backward-PTS cases the way MP4SegmentMuxer.bufferedTicksExceedsBound does. Separately, cap in-memory growth of the never-cut first segment: when pendingSegmentBytes/progressiveSegments exceed a byte budget (e.g. a few hundred MB), either spill the progressive prefix through the PR #68 disk-spill tier in LoopbackSegmentStore or fail the session with a new LoopbackWriterError (mirroring vodStartupConsumerWedge) so the route ladder falls back to PlayerCore instead of jetsam.

### live-streaming — `not_applicable`

AetherEngine's live-streaming cluster hardens live/DVR playback: dead-source retune surfacing, live-rejoin at the playlist edge without stale resume clocks, lean-live self-start, trickle-vs-wedge rate classification, SSAI per-stream timestamp re-anchoring, playlist-refresh retry budgets, stream-replay detection, LL-HLS handling, AVERAGE-BANDWIDTH variant parsing, and DVR ring-buffer keyframe-aligned seeding/eviction. Silo's Apple client has no live, broadcast, DVR, channel, EPG, or SSAI surface anywhere — every playable item is library VOD (movie/episode/audiobook) remuxed through the local loopback into a static #EXT-X-PLAYLIST-TYPE:VOD/#EXT-X-ENDLIST presentation, so 12 of 13 members' failure modes structurally cannot occur: there is no remote live playlist to poll (the playlist is generated and served from localhost by LoopbackSegmentServer), no live edge to rejoin, no ad-stitched creatives, no client-side multi-variant master parsing (we generate single-variant masters, PR #67, and never parse AVERAGE-BANDWIDTH), and no DVR ring buffer (the legacy .event mode's retention evicts only whole keyframe-cut fMP4 segments, so mid-GOP eviction is impossible by construction). The single member shared with VOD — #95 playlist-time-to-segment-index mapping — IS applicable and is covered: LoopbackSegmentPlan.segmentIndex(forPlaylistSeconds:) walks the real per-segment startSeconds fence array with clamping (the cumulative-EXTINF-walk invariant), never naive division by target duration, and that mapping is what AVPlayerBackend uses for restart/seek anchoring. AE #3.6.1's rate-based wedge-vs-trickle classifier conceptually maps onto our already-flagged deferred steady-state backpressure wedge detector (known open, not re-reported); its live-specific consequence (premature retune of a healthy live stream) has no analog here.

### teardown-generation-races — `covered`

AE's teardown cluster fixed: main-thread freezes from synchronous stop (detached cleanup + waiter cancellation), a main-actor-blocking FFmpeg probe, stop() queuing behind a restart wait, session identity surviving stop (background hooks resurrecting playback), a queued audio switch reviving a stopped session, seeks finalizing mid-stop, stale live-seek finalize, and an unsynchronized demuxer close-flag race. We enforce every applicable invariant, mostly via different mechanisms: (a) LoopbackSegmentWriter.stop() is non-blocking (cancel flag under cancelLock + interrupt-token cancel + file cleanup deferred to a muxQueue completion), and PlayerCore.dispose() drains packet queues / wakes decode waiters BEFORE its demuxQueue.sync{} barrier — the code comments at PlayerCore.swift:1998 document independently discovering and fixing the exact 'barrier hangs on a parked cond' freeze AE hit; parked FFmpeg I/O is bounded by an interrupt callback installed before avformat_open_input. (b) Waiter cancellation exists: PlaybackSourceProxy resource stop() resumes all data/total continuations and cancels serve tasks; segment-store waits are bounded 0.25s polls with deadlines, and per-generation store instances/directories make AE's stale-write-into-recycled-fd impossible. (c) Probe/open runs off-main (demuxQueue.async / muxQueue; server bind via checked continuation instead of a semaphore). (d) Our sessionEpoch equivalent is activeLoopbackSessionID + isDisposed, nil'd/set in teardown and re-checked on every async hop, with restart and teardown both @MainActor-serialized and non-blocking so stop never waits on a restart. (e) PlayerViewModel.cleanup() clears session identity (activePlaybackSessionId, activePlayer = .none), cancels all recovery tasks, and clears interruption/suspend state so scene-phase/foreground hooks cannot resurrect playback. (f) Deferred audio-track switches apply only under !isDisposed (commits 4f1e097/c69d65a). (g) All VM state callbacks guard !isDisposed, killing phantom post-stop .playing.
